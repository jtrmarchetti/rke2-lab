# Flux / Ansible ownership boundary

Scope: the `dev-lo` cluster. The cluster-state repo is generated by the
`gitops_source` role from the Jinja templates under
`ansible/files/gitops_source/cluster-state/`, pushed to GitLab, and reconciled
by Flux v2.9.4 (helm-controller 1.6.3, kustomize-controller 1.9.4). This page
records the standing decision of **what Flux owns and what Ansible covers**,
the capability that drove the split, and the feature-adoption bar for the
rest of the tree.

## The rule

Flux owns every in-cluster Kubernetes object it can reach through the
GitOps tree. Ansible covers the **gaps** — the things Flux fundamentally
cannot see or do:

- one-time bootstrap that happens before/around GitOps existing at all;
- provisioning into **external** systems (OpenBao vault, Keycloak, FreeIPA,
  the Garage S3 store) rather than into the cluster;
- host-level and out-of-band configuration;
- out-of-band markers and one-time operational recovery.

Anything that is a static in-cluster object and has no ordering dependency on
the gaps above belongs in the tree.

## Capability that drove the split (Flux v2.9.4)

Probed live on the cluster — these are the primitives available; the audit
assumes nothing the CRDs do not actually expose.

| Primitive | Where | Used for |
|---|---|---|
| `spec.dependsOn` | Kustomization | Blocks **apply** of a KZ until the listed KZs are Ready (build-ordering). |
| `spec.healthChecks` | Kustomization | Holds a KZ not-Ready while a named in-cluster object (any apiVersion/kind/namespace, e.g. a ConfigMap) is absent; retries at `retryInterval`, never terminal. **Ignored when `spec.wait: true`** — a gate KZ must therefore not set `wait`. |
| `spec.wait` | Kustomization | Waits for applied resources to become Ready before reporting Ready. |
| `spec.driftDetection` | HelmRelease | `mode: enabled\|warn\|disabled` (+ `paths`) — diffs the Helm manifest against the live object. `warn` is observational only. |
| `spec.waitStrategy` | HelmRelease | Defaults to `poller` (kstatus) already. Nothing to adopt. |

Not present in v2.9.4 (confirmed by probing the installed CRDs, not recall):
Kustomization `gates`, `readiness`, `readFrom`, and `readyExpr`-style CEL
gating is only available as `spec.dependsOn[].readyExpr` / HelmRelease
`healthCheckExprs` (CEL over in-cluster objects — it cannot observe the
out-of-band markers that Ansible produces, which is exactly why the gate below
uses a `healthChecks` ConfigMap check instead).

## The garage gate (the worked example)

Observability needs the Garage S3 buckets usable, which Flux cannot see on its
own. The split:

- **Ansible owns the marker.** `garage_init` finishes by publishing
  `ConfigMap garage-buckets-ready` in `namespace: garage`
  (`data.buckets: "longhorn-backups loki tempo"`). That object intentionally
  lives *outside* the Flux tree.
- **Flux owns the gate.** `clusters/dev-lo/garage-ready.yaml` — a dedicated
  Kustomization whose readiness *is* the marker check (`spec.healthChecks` on
  that ConfigMap). It applies an inert in-repo marker ConfigMap so the build is
  never empty, sets **no** `wait`, and `retryInterval: 2m`.
- **`observability` depends on the gate.** `clusters/dev-lo/observability.yaml`
  sets `dependsOn: [apps, garage-ready]` and its own `wait: true`, so its four
  releases (loki, tempo, alloy, kube-prometheus-stack) are held until the
  marker exists. On a cold build the gate stays not-Ready until
  `garage_init` runs; on a warm cluster the marker pre-exists and the gate is
  Ready from the first reconcile.
- `observability` was removed from the `apps` build. The one-time GC
  ownership transfer (`apps` → `observability`) is expected; S3 data in Garage
  and longhorn PVCs persist, so it is non-destructive for durable data.

`flux_unstall` remains as the out-of-band recovery path for the rare terminal
`Stalled` HelmRelease that a health-check gate cannot express.

## Ownership boundary, role by role

| Ansible role / playbook | What it writes | Class | In Flux? |
|---|---|---|---|
| `gitops_bootstrap` | Flux controllers, GitRepository + root KZ, `flux-system` repo-credential Secret, sealing-key Secret (restore-only) | One-time bootstrap | No — out-of-band by definition |
| `garage_init` | Garage layout/bucket/key ops (`kubectl exec` in-pod); **marker ConfigMap `garage-buckets-ready`** | Gap: store layout + out-of-band marker | No |
| `openbao_init` | `kubectl exec` init/unseal | One-time vault bootstrap | No |
| `openbao_secrets`, `openbao_config`, `openbao_oidc` | OpenBao KV + config via `uri` | Secret provisioning (external) | No |
| `keycloak_realm` / `_clients` / `_realm_admins` / `keycloak_break_glass` | Keycloak admin API via `uri` | App-config into an external system | No |
| `keycloak_ldap` | FreeIPA `ldapmodify` + Keycloak admin API | Identity-store provisioning | No |
| `ipa_service_cert`, `ipa_sso_groups`, `ipa_sub_ca` | FreeIPA only | Out-of-cluster identity | No |
| `split_dns`, `socks5_proxy`, `wireguard_gateway`, `rke2_*`, `container_storage`, `data_volume`, `longhorn_node` | Host files, RKE2 systemd, docker/containerd, disk layout; node-local `kubectl` **read-only** readiness | Host bootstrap / out-of-band | No |
| `helm_cli`, `kube_cli_controller`, `kube_cli_node` | Binary installs on hosts | Tooling | No |
| `rke2_publish` | GitLab registry/chart publishing | Artifact publishing | No |
| `flux_unstall` | `flux suspend/resume helmrelease` (repair only) | Out-of-band recovery | No |
| `kubewk.yml` | Node label + `CriticalAddonsOnly` taint | One-time node bootstrap | No |
| `validate_phase5.yml` | Ephemeral test namespace (create/delete) | Test scaffolding | No |

Every other in-cluster object (Flux Kustomizations, the controller and app
HelmReleases, ConfigMaps, ExternalSecrets, namespaces, ingress, the garage
StatefulSet, keycloak, longhorn-auth) is owned by the GitOps tree.

## Feature adoption

Current bar for the tree (all HelmReleases, all Kustomizations):

- `interval` 30m, per-release `timeout`, `install`/`upgrade`
  `remediation.retries` — already set on every release.
- `wait: true` on the KZ chain that must settle before the next tier
  (`infra-controllers` → `infra-configs`/`unsealer` → `apps` →
  `observability`); **not** on `garage-ready` (its readiness is the marker
  check, so `wait` would disable the health check).
- `driftDetection: {mode: warn}` on every HelmRelease — observational drift
  diffing into the Flux event feed; it never blocks or mutates, so it is safe
  on a green cluster. Adopting now; `enabled` (auto-remediation) is a future
  decision, not a default.

Not adopted, and why:

- `waitStrategy` — already defaults to the `poller` strategy; setting it
  explicitly changes nothing.
- `postRenderers` / `postRenderStrategy` — no release needs an image/patch
  transform today; introducing a tree-wide kustomize-internal patch risks
  clobbering the Flux GC owner-labels, so it is deferred until a concrete
  need appears.
- CEL `healthCheckExprs` — no release needs sub-object readiness CEL today;
  the KZ-level `healthChecks` gate covers the only known ordering need
  (Garage). Revisit if a specific release needs per-field gating.

## Maintenance notes

- The gate marker name is **hardcoded** in
  `clusters/dev-lo/garage-ready.yaml` and must stay in sync with
  `garage_init_marker_name` (documented in `roles/garage_init/meta/argument_specs.yml`).
- If the marker is ever removed or renamed, update the gate template, the
  `garage_init` default, and re-push the tree in the same change.
- The `ca-keypair.yaml` under `infrastructure/controllers/cert-manager/` is a
  **seal step artifact** (generated by `gitops_source`), not a missing
  manifest — do not "fix" it by adding a real file.
